Learning Kudu · Part 8

How a scan works

A scan is how every query reads Kudu, whether it comes from Impala, Spark or your own code. The system's design choices from earlier parts all pay off here: columnar files, row numbers, MVCC snapshots, bloom filters and partition rules. This part follows a scan from the client's options to the bytes of one column block, and shows where each filter prunes work.

The path of a scan

A scan covers a range of a table, so it usually touches many tablets, but it reads one tablet at a time through one scanner object. The client walks the tablets, and for each one it opens a server-side scanner, pulls batches until the tablet is exhausted, and moves on. On the server a scan is a tree of iterators that read rows in blocks of 128.

What the client decides

A KuduScanner is configured before it is opened. These settings decide which of the guarantees and costs below you get.

Choosing which tablets to ask

Before sending any RPC, the client works out which tablets can possibly contain matching rows, using the table's partition schema from Part 3. This is partition pruning. It is the cheapest filter in the whole system, because the tablets it removes cost nothing at all.

Scan tokens: splitting a scan across workers

A distributed engine wants to cut a table scan into tasks, ship each task to a worker, and run them in parallel, ideally on the machine that holds a replica. A scan token is a small serialized description of one such task. It carries the table, projection, predicates, snapshot choice and a partition key range, so any process with a Kudu client can rebuild a scanner from it.

Opening a scanner on the server

The first RPC for a tablet carries a NewScanRequestPB. The handler turns it into a ScanSpec (the predicates and key bounds), simplifies it, and builds the iterator. Most of the checks run before any file is touched, which makes rejections cheap.

Which version of the data? Snapshots

Step ⑦ is where MVCC (Parts 5 and 6) decides what a scan sees. An MvccSnapshot is a set of timestamps whose changes count as committed. The three read modes pick that set differently, and trade waiting against consistency. The picture uses one tablet where several writes are in flight.

The iterator tree

The server reads rows through RowwiseIterator objects that hand over one block at a time. The shape of the tree comes from the tablet's components (Part 6): one MemRowSet iterator, one iterator per candidate DiskRowSet, and one combining iterator on top.

Reading one batch from a DiskRowSet

Inside a rowset the iterator works on blocks of up to 128 rows, numbered by their row number. For each block it builds a selection vector, one bit per row, and clears bits as filters reject rows. Columns that have a predicate are read first. If the predicate rejects the whole block, the other projected columns are never read, so their blocks stay on disk.

Every filter in one picture

Each stage removes work earlier and more cheaply than the next. When a scan is slow, the useful question is at which stage the data stopped being pruned. The numbers below are an illustration.

Batches, keep-alive and the scanner's lifetime

After the open call, the client keeps asking for more. Each request names the scanner and carries a call sequence number, so a duplicate or reordered request cannot return rows twice.

When a server fails mid-scan

Scanner state lives only in the memory of one tablet server. If that server stops, or the scanner times out, the scan cannot simply continue. Kudu offers two behaviors.
