Multi-tablet transactions

A normal Kudu write is atomic inside one tablet. A transaction lets a client insert rows into many tablets and make them all appear at once, or not at all. This part shows who coordinates that, the states every tablet goes through, the commit protocol, and why a reader never sees half a transaction. It is a young feature: read the limits section before relying on it.

Four actors

Single-tablet writes already get atomicity from Raft and the WriteOp path (part 5). A transaction needs something above that: a durable record of "this transaction is open / committing / done" that survives failures, and a way to tell every tablet touched what the outcome is. Kudu builds this out of its own parts.

TxnManager is a service on the masters. Clients talk only to it; it hands out transaction IDs and forwards each request to the right place. The transaction status table is a special, system-created Kudu table (range partitioned by transaction ID). Its tablets are replicated with Raft like any other, and each hosts a TxnStatusManager in its leader, which holds the state of the transactions in that ID range. Participants are the ordinary data tablets that received writes for the transaction. The client writes rows straight to the tablet servers as usual.

The status table is created by the masters when the feature is first used. The relevant flags are experimental: --txn_manager_enabled is false by default, and the system client the tablet servers use to talk to participants is gated by --enable_txn_system_client_init (also false). A new range partition of --txn_manager_status_table_range_partition_span IDs (default 1,000,000) is added when TxnManager finds an ID with no tablet, and the table has --txn_manager_status_table_num_replicas = 3 replicas.

The coordinator's state machine

For each transaction the TxnStatusManager keeps one entry (TxnStatusEntryPB): the state, the user who started it, the commit timestamp once chosen, and the list of participant tablets. Every change is a Raft write to the status tablet, so a new leader reloads exactly the same view.

Participants: joining a transaction

The client does not tell the coordinator which tablets it will use. A tablet registers itself the first time it receives a write that carries a transaction ID. Until registration finishes the tablet holds the incoming writes back (up to --tablet_max_pending_txn_write_ops per transaction, default 2, then it tells the client to retry). The steps:

  1. A Write RPC with txn_id arrives at the leader of tablet A. A is not yet a participant, so the write is parked in a per-transaction dispatcher.
  2. A asks the status tablet to register it as a participant. The coordinator checks that the transaction is still OPEN and records A in the entry. Registration after commit or abort began is refused.
  3. A replicates a BEGIN_TXN op through its own Raft group. That creates the transaction on every replica of A, with a transactional MemRowSet for it.
  4. The parked writes run, and so do later ones, which now skip the registration step.

Commit: choosing one timestamp for everyone

Think of a two-phase commit where the first phase gathers timestamps rather than votes. Every participant stamps its BEGIN_COMMIT op with a hybrid-clock timestamp (part 5). The coordinator picks the largest of them as the commit timestamp, so the commit time is later than every participant's own BEGIN_COMMIT. Then FINALIZE_COMMIT tells each participant the final value.

Failure handling. If a BEGIN_COMMIT cannot be delivered or fails, the coordinator moves to ABORT_IN_PROGRESS and sends ABORT_TXN to every participant, which drop the transaction's rows. After FINALIZE_IN_PROGRESS the coordinator retries until every participant accepts; the transaction is committed from that moment even if a tablet server is down, and that tablet will apply the commit when it returns. Background requests use --txn_background_rpc_timeout_ms (default 5000) and run on a pool of --txn_commit_pool_num_threads (default 10) threads on each tablet server.

Waiting for it. The client's Commit() by default starts the commit and then polls until the state is COMMITTED (or fails if aborted). StartCommit() returns right away and IsCommitComplete() can be polled.

What a reader sees

Transactional rows are kept apart from normal rows until commit. Each tablet keeps the usual MemRowSet and, for each open transaction, a separate MemRowSet tied to a TxnMetadata record. A scan then asks one question about each transactional MemRowSet: is this transaction committed as far as my snapshot is concerned?

The rule differs a little by read mode: for timestamp snapshots (READ_AT_SNAPSHOT, READ_YOUR_WRITES, diff scans) the transaction must be committed and its commit timestamp must fall inside the snapshot; for READ_LATEST it is enough that the BEGIN_COMMIT op has been applied, because Kudu applies it only after FINALIZE_COMMIT has replicated. Once a BEGIN_COMMIT has replicated, the tablet refuses more writes for that transaction.

Memory and flushing. A transaction's MemRowSet is not flushed while the transaction is open. After commit, all committed transactional MemRowSets are flushed together, like a merge compaction, and each row gets the commit timestamp on disk; scans of disk data then never need the transaction metadata. Their memory counts together for the flush decision (part 7).

Locking: one transaction per tablet at a time

Besides the per-row locks every write takes, a transaction takes a partition lock on the whole tablet, and each tablet has exactly one. This is what gives the "at most one open transaction per tablet" limit. To avoid deadlock Kudu uses the wait-die rule on transaction IDs (smaller means older). Heartbeats and abandoned transactions

A client that crashes would leave a transaction open and its tablets locked forever. So an open transaction must be kept alive. A handle created by NewTransaction() sends keepalive messages from a background thread at an interval related to --txn_keepalive_interval_ms (default 30 s). The status manager runs a staleness tracker every --txn_staleness_tracker_interval_ms (default 10 s); a transaction with no keepalive for longer than the keepalive interval is aborted automatically, which releases the tablets' locks. Setting the tracker interval to 0 disables it.

A transaction can also be handed to another process (for example a Spark driver giving work to executors) by serializing the handle into a token. Whether the copy sends keepalives is a serialization option, off by default: the original handle should keep the transaction alive while workers write.

Limits and caveats

  • Experimental. The feature flags above are tagged experimental or hidden, and the master side is off by default. Check docs/transaction_semantics.adoc in your release for the supported statement.
  • Inserts only. According to the design doc, transactions support INSERT (and INSERT_IGNORE); updates and deletes of rows inside a transaction are not supported yet. I did not exhaustively confirm in the code which operation types are rejected.
  • One transaction per tablet at a time, because of the partition lock. Two concurrent transactions that touch the same tablet conflict, and the younger one aborts.
  • Isolation. Reads outside the transaction see committed data under the usual snapshot rules; the documented guarantees are atomicity and visibility at the commit timestamp, not serializability. Read transaction_semantics.adoc for the exact statement, including what a transaction can read of its own writes.
  • Cost. Commit touches the status tablet several times (each state change is a Raft write) and every participant twice. It is meant for batches, not for single-row work.
