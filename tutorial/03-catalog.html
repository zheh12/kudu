Inside a master

A master is a small server built on the same RPC stack as Part 2. Its job is bookkeeping, so it is not on the path of any read or write. Only the leader master serves catalog requests. The others keep a copy of the data and wait to take over.

What the catalog stores

Two kinds of objects matter. A TableInfo holds the schema, partitioning rules and replication factor. A TabletInfo holds one tablet's key range, its state, and the latest Raft configuration the master has heard about, including who the leader is. Each is saved as a row in sys.catalog, whose schema is just three columns.

Tablet and table states

Both objects move through small state machines. Every transition is written to sys.catalog before it becomes visible in memory. The state names below are the enums in master.proto.

CreateTable, step by step

Creating a table is two separate jobs. The first runs inside the RPC and ends with the table recorded in sys.catalog. The second runs in the background and actually creates tablet replicas on tablet servers. This is worth knowing: the call can return before any tablet exists.

Part 1's design doc describes the table and tablets being written in two phases. The current code writes them together in one sys.catalog write, and the tablets start in PREPARING.

How a table becomes tablets

Step ② decides how many tablets there will be. Hash partitioning spreads writes across buckets. Range partitioning keeps neighbouring keys together and lets you add or drop ranges later. When a table uses both, the tablets are the product: every hash bucket in every range.

Creating the replicas

Now the background thread takes over. Once a second (or immediately when woken by CreateTable) it collects every tablet that is neither running nor deleted and calls ProcessPendingAssignments. Here is what happens to one new tablet, from the master's first look to the moment clients can use it.

Choosing where replicas go

The master's PlacementPolicy avoids a global sort. For each replica it draws two random tablet servers and keeps the less loaded one, then repeats with those servers excluded. This is the "power of two choices" idea: it balances well, it is cheap, and it does not send every new tablet to the one emptiest server.

How the master learns what happened

The master never polls tablet servers. Each one sends a TSHeartbeat every second to every master. Only the leader acts on it. The heartbeat is also how the master finds out that a replica was created, who its leader is, and which schema version it runs.

How a client finds a tablet

Back in Part 1, the client's first step was GetTableLocations. Here is the master's side of it. The table keeps its tablets ordered by partition key, so a key range maps to a short list of tablets, and each tablet already carries the replica addresses and leader it learned from heartbeats.

Altering and deleting

The same pattern repeats: change the catalog first, then tell the tablet servers asynchronously and keep retrying. Heartbeats are the safety net, because a server that missed an RPC will show the wrong state in its next report.

When the leader master dies

Masters form a Raft group over sys.catalog. If the leader fails, the remaining masters elect a new one. The new leader has the data (it replicated every write) but not the in-memory state, so it rebuilds that state before it serves requests.
