Tracing one write

Parts 1 to 4 explained the pieces. This part uses them all. We follow a single INSERT from your application call to the row sitting in a MemRowSet on three servers, and name the thread, the lock and the source function at every step.

The whole trace on one page

The example is one row written to the metrics table from Part 3: key (host, time), one nullable cpu column. The row is ('web-3', 1735689600, 0.42). Hashing host puts it in bucket 1, and the time falls in the first range, so it belongs to tablet T1, whose leader is on tablet server TS-2.

Thirteen steps run on seven kinds of thread. A call never stays on one thread for long: each hand-off is a queue, and each queue is a place where a busy server pushes back.

Steps 1 to 3: the client builds the request

The application hands a row to a KuduSession. The session gives it to a Batcher, which has two jobs: find which tablet owns each row, and bundle rows for the same tablet into one RPC. The flush mode decides when the bundle leaves.

What is in the request

The request is a WriteRequestPB. Its rows are not protobuf fields but one compact byte string, RowOperationsPB.rows, so that the server can decode thousands of rows without allocating an object per cell. Variable-length values such as strings sit in a second buffer.

Step 5: the gates in front of the tablet

A service worker picks up the call and runs TabletServiceImpl::Write. Before it commits any server resources to the write, it runs a series of cheap checks. Each can refuse the request. The client treats most refusals as "try again soon, perhaps elsewhere".

The OpDriver: two tracks that meet

From here on, an operation is owned by an OpDriver. The driver tracks two independent progress markers: has the operation been prepared locally, and has it been replicated? The operation is applied only when both are true. The same class drives leaders and followers. They differ only in the starting state.

Step 6 and 7: Prepare, then a timestamp

WriteOp::Prepare turns bytes into row operations and takes locks. The driver then assigns the timestamp and calls Raft. The order matters: locks come before the timestamp.

Steps 8 and 9: replicate and wait

This is Part 4 in one line. Replicate gives the operation an OpId such as 7.413. The leader writes it to its WAL while sending UpdateConsensus to each follower. When the leader's own WAL write and one follower's acknowledgement are both in, the commit index passes 7.413. Raft's apply callback then calls OpDriver::ReplicationFinished, which moves the replication track to REPLICATED and submits the apply task.

What is stored in that log entry matters for step 10: the entire request, plus the leader's timestamp. Followers and crash recovery replay it from there.

Step 10: Apply, finally touching the data

An apply-pool thread runs WriteOp::Apply, which calls Tablet::ApplyRowOperations. This is the first time any row reaches a store. The tablet first marks the MVCC op as applying and takes a consistent view of its components (the current MemRowSet and the set of DiskRowSets), then probes and writes.

Steps 11 and 12: commit, release, answer

The rows are in memory but nobody can see them yet. The driver now finishes in a precise order. The order is the reason readers never see half of a batch and writers never see stale rows.

Meanwhile on the followers

The two followers run the same WriteOp, from a different entrance. They have no client and no RPC to answer, so they run fewer steps. They keep the leader's timestamp so that every replica ends up with identical MVCC histories.
