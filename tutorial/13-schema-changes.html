Schema changes and alter table

A Kudu table can change while it is being read and written: columns come and go, and range partitions are added and dropped. The master records the new schema first, then pushes it to every tablet through Raft, while old data on disk keeps its old shape and is reconciled when it is read. This part follows one ALTER TABLE end to end and explains the ideas that make it safe: column IDs, schema versions, and read-time projection.

What can be altered, and what cannot

An alter request carries a list of steps, applied in order and committed together as one transactional change to the table. The master's step types are ADD_COLUMN, DROP_COLUMN, RENAME_COLUMN, ALTER_COLUMN, ADD_RANGE_PARTITION and DROP_RANGE_PARTITION. The same request can also rename the table, change its owner or comment, and set some table properties (extra configs, disk-size and row-count limits, replication factor).

Column IDs: names are not identity

Clients refer to columns by name. Inside the server every column also has a numeric column ID that is never reused. The table metadata keeps a counter (next_column_id) that only grows. IDs are internal; a client may not set one (an ADD_COLUMN that includes an ID is rejected).

Why do this? Because a name can be reused for different data. The design doc's example drops col_b and adds a new col_b. Old rows must show the new column's default, not the old values that still sit in old files.

The alter flow, step by step

The master is the source of truth for the schema, so it persists the change before any tablet knows about it. Tablets then catch up one by one. The table state is ALTERING until all of them have.

The default for the client is to wait: KuduTableAlterer::wait(true). Alter() then keeps asking IsAlterTableDone until the master says it is done or the timeout expires. A timeout does not cancel the alteration; it only stops the client from waiting.

When is the alter "done"?

The master tracks the schema version each tablet last reported (heartbeats carry it), in a small histogram per table. An alter is in progress while the lowest reported version is below the table's current version, or while some tablet has not reported at all. While it is in progress the master keeps both schemas: the current one and the fully_applied_schema, the last schema that every tablet is known to have. Metadata requests during that time return the fully applied schema, so a client does not start using a column that some tablets do not have yet.

What a tablet does

The tablet server's AlterSchema handler is careful to be repeatable, because the master may send it several times (after a failover, or when a lagging replica reports an old version):

  • If the tablet already has exactly the requested version, it just replies "done". It also checks the schema is the same one the request names, and answers with an error code if not (MISMATCHED_SCHEMA).
  • If the tablet has a newer version than the request, it rejects the request (TABLET_HAS_A_NEWER_SCHEMA) and the master's retry stops mattering.
  • Otherwise it submits an AlterSchemaOp through consensus, like a write (part 5), so every replica changes at the same point in the log.
  • On apply, the op takes the tablet's schema lock in exclusive mode. Write ops hold it in shared mode for their whole life, so the alter waits for in-flight writes and briefly blocks new ones. It also blocks concurrent flushes, because a MemRowSet's schema cannot be changed in place.
  • It installs the new schema and version in the tablet metadata (and the table name or extra config if those changed) and then flushes the MemRowSet so no in-memory data has the old shape. The op's commit message is logged, and only then is the lock released, as a workaround noted in the code (KUDU-915).
Tablet bootstrap (part 6) rewinds the schema to what was in effect when each logged op was written, so replaying the WAL after a restart still decodes old writes correctly.

Reading data written under older schemas

An alter does not rewrite files. A tablet can therefore hold rowsets written under several schemas at once. When a scan runs, the tablet picks a read schema from its current metadata and each rowset projects its data onto it.

Range partitions in an alter

Adding or dropping a range is part of the same request, and the master works out the tablets involved while processing the steps. For an added range it creates the new tablet metadata (one tablet per hash bucket for that range) and the tablets get created through the normal path from part 3. For a dropped range it marks those tablets deleted and sends delete requests after the sys.catalog write commits. The table's cached locations are invalidated so clients re-fetch them.

What clients and writes see during an alter

Clients identify columns by name, type and nullability, never by ID. A write or scan names the columns it wants, and the server maps names to current IDs. A name that no longer exists is an error; a type or nullability mismatch is also an error. A client that opened its table handle before the alter keeps working as long as the columns it uses still exist, and a long-lived handle sees the new schema after it refreshes the table (open the table again).

In the Java and C++ clients the alterer is a builder: NewTableAlterer(name), then AddColumn(...) / DropColumn / AlterColumn with a KuduColumnSpec (default, encoding, compression, block size, comment, rename, nullable, immutable), RenameTo, AddRangePartition / DropRangePartition, SetOwner, SetComment, timeout and wait, and finally Alter(). SQL engines map their ALTER TABLE statements onto the same calls.
