The architecture of Apache Kudu

Kudu is a distributed, columnar storage engine for fast analytics on data that keeps changing. This part walks from the whole cluster down to the files on one disk. Every name below comes from the source in src/kudu/.

The whole cluster at a glance

A Kudu cluster has only two kinds of server process. Masters remember what tables exist and where their pieces live. Tablet servers store the rows and answer reads and writes. Clients ask a master once where to go, then talk to tablet servers directly.

Who does what

Master

The cluster's catalog and coordinator. Never on the data path of a read or write.

  • CatalogManager owns table and tablet metadata, kept in memory and persisted in sys.catalog.
  • TSManager tracks live tablet servers from their heartbeats.
  • Picks replicas for new tablets, and re-replicates when a server dies.
  • Hands out tokens, runs authorization (Ranger) and the optional Hive Metastore sync.

Tablet server

Hosts many tablet replicas. Each replica is a small database with its own Raft log.

  • TSTabletManager creates, opens, deletes and copies replicas.
  • TabletServiceImpl serves Write and Scan RPCs.
  • A Heartbeater thread reports to the master.
  • A MaintenanceManager schedules flushes, compactions and log GC.

Client

A library linked into your application. It does the routing, so there is no proxy tier.

  • MetaCache remembers tablet locations and refreshes them on errors.
  • Batcher groups row operations by tablet before sending.
  • Retries and fails over to another replica when a leader moves.
  • Python and Spark sit on top of the C++ and Java clients.

From table to tablets to replicas

A table is cut into tablets by hash buckets, key ranges, or both. Each tablet is copied to several tablet servers (default_num_replicas is 3). The copies form a Raft group: one leader takes writes, the followers copy its log. A server holds replicas of many tablets, so load spreads across the cluster.

Inside one tablet server

An RPC arrives at the top and works its way down. The kudu::rpc layer decodes it and queues it for a service thread. The service finds the right TabletReplica. The replica runs the operation through Raft and then applies it to the Tablet, which reads and writes files through the FsManager.

How one tablet stores rows

A tablet is a set of RowSets. New rows go to a single in-memory MemRowSet, a B-tree sorted by primary key. When it grows large or old, the maintenance manager flushes it to a DiskRowSet. A DiskRowSet stores each column in its own file, so a scan reads only the columns it needs.

Every change carries a timestamp. Updates to flushed rows are written as small REDO deltas, and the older values are kept as UNDO deltas. A reader picks a snapshot timestamp and applies whichever deltas bring each row to that moment. This is MVCC, and it is why scans see a consistent view while writes continue.

Why this design: columnar base data makes analytic scans fast, while sorted MemRowSet inserts plus small deltas keep random writes cheap. The cost is background work, so watch compaction health when tuning.
