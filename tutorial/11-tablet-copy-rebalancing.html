Tablet copy and rebalancing

Raft keeps replicas in step by replaying a log, but a brand-new replica has no history and an old log is eventually deleted. Tablet copy solves both: it ships a consistent snapshot of a tablet's files from one server to another. Rebalancing is the policy layer that decides which replicas to move so servers carry an even load. This part follows a copy from the trigger to the last byte, then shows how a replica move and the rebalancer tool are built on it.

Three situations that need a copy

The WAL (part 4) lets a follower that is a little behind catch up by replaying ops. It cannot help when the follower has no data at all, or needs ops the leader has already thrown away. In both cases the leader tells that follower to fetch a snapshot instead.

The protocol, step by step

The target is the active party. After the leader's StartTabletCopy it opens a session with the source, pulls every file, then swaps in the new tablet atomically. The source is only a file server for a frozen view of the tablet. Here the example is a new replica added through a configuration change.

The leader promotes a caught-up NON_VOTER to VOTER itself (RaftConsensus::NotifyPeerToPromote). While the new replica is a non-voter it never counts toward a majority, so a slow or failed copy does not endanger the tablet's availability. This is the "3-4-3" scheme from part 4.

What happens on each side

Replacing an existing replica. A server that already holds a tombstoned replica of the tablet can be the target. The client first calls SetTabletToReplace with the leader's term; if the term is lower than what the local consensus metadata remembers, the copy is refused. That protects against a stale leader overwriting newer state.

Errors and retries. A copy that cannot finish is cleaned up locally and the leader tries again the next time it sees the replica missing (the exchange still says TABLET_NOT_FOUND or the replica is tombstoned). The begin and end calls time out after --tablet_copy_begin_session_timeout_ms (30 s).

Metrics you can watch on both sides: tablet_copy_bytes_fetched, tablet_copy_bytes_sent, tablet_copy_open_client_sessions, tablet_copy_open_source_sessions and the duration histograms.

Moving a replica: add first, remove later

Kudu never moves a replica by deleting it and hoping. A move is a configuration change in two parts, using the "replace" attribute introduced for the 3-4-3 scheme. The tool (or the master during re-replication) only asks; the leader and the master carry it out.

Automatic re-replication uses the same pieces. A leader that cannot reach a follower for --follower_unavailable_considered_failed_sec (300 s) marks it failed; with --evict_failed_followers (true) it is replaced as above. The master also removes excess replicas (--catalog_manager_evict_excess_replicas) and tombstones replicas that are no longer in the latest configuration (--master_tombstone_evicted_tablet_replicas).

Rebalancing: deciding what to move

Kudu has no background balancer on the servers. Placement of new tablets is already spread by the master, but after you add servers, or after a failure and re-replication, the cluster can become lopsided. Balance is restored by running kudu cluster rebalance, an ordinary CLI tool that reads cluster state, plans moves and issues the replica moves above through the same RPCs any admin would.

The planner is a greedy, two-dimensional algorithm (rebalance/rebalance_algo.h). Skew of a table is the difference between the most and the least loaded tablet server for that table; skew of the cluster is the same for total replica counts. The cluster is "balanced" when every table has skew ≤ 1 and the cluster skew is ≤ 1. Each step picks a move that lowers the skew of the most skewed table and, among those, prefers one that also lowers the cluster skew.

Range rebalancing. With --enable_range_rebalancing (true), the rebalancer also balances each range partition of a table separately, so one hot time range does not end up on one server. Moves are real work: each is a tablet copy plus a config change, so the tool limits concurrency to --max_moves_per_server (5), counting "move from" and "move to" separately.

Running the rebalancer

  1. Start with a report: kudu cluster rebalance <masters> --report_only. It prints per-table and per-server skew and exits. Add --output_replica_distribution_details for the full tables.
  2. Run it for real. It first reports, then schedules moves in waves, checks each for completion (the new replica is a voter and the old one is gone) and re-reads the cluster state until nothing is left to do.
  3. It is safe to stop at any time: a half-finished move is just a normal configuration change, and a re-run continues from the current state. Use --max_run_time_sec to bound a run and --tables to limit it to certain tables (then it does not balance the cluster as a whole).
  4. All registered tablet servers must be up, otherwise the tool exits, to avoid fighting with automatic re-replication. Servers you are about to decommission can be listed in --ignored_tservers; with --move_replicas_from_ignored_tservers (and the servers in maintenance mode) the tool drains them.
