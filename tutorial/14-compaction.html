Compaction: a deep dive

Part 6 introduced compaction in a paragraph. This part opens it up. Kudu has several different background rewrites, each fixing a different kind of mess: too many overlapping files, too many small delta files, updates that have not reached the base data, history that is too old to keep. We cover what each one does, how the rowset compaction policy chooses what to merge (a small knapsack problem), how a merge runs while writes continue, and how the maintenance manager decides when any of it happens.

Six operations, three kinds of mess

Recall the tablet layout from part 6: a MemRowSet in memory, and on disk a number of DiskRowSets, each holding immutable base data (one column file per column, plus bloom filter and key index), REDO delta files (updates and deletes after the base was written) and UNDO delta files (how to roll the row back to older versions). Every write path ends in one of these background jobs.

Why overlap is the enemy: width and height

A DiskRowSet covers a range of primary keys, from its smallest to its largest key. Two measures from the design doc (compaction-policy.md) explain everything the merge policy does:

Width of a rowset is the fraction of the tablet's key space it spans, which is also the chance a random read has to consult it. Height at a key is how many rowsets contain that key, which is how many rowsets a read or an insert of that key must check (a bloom filter probe and, on a hit, a key lookup). Scans cannot use bloom filters, so they seek in every overlapping rowset.

The policy: a bounded optimization

Kudu's BudgetedCompactionPolicy turns the idea above into a precise search. Given all the tablet's rowsets, pick the set whose benefit is largest while the total size of its inputs fits a budget. Choosing which rowsets fit under a size limit to maximize a total is the classic 0-1 knapsack problem.

Consequences you can see in a cluster. A uniform random insert load flushes rowsets that all span the whole key space, so the height grows with each flush and merges are valuable. A time-ordered insert load flushes rowsets that already sit side by side, so the policy finds little benefit and mostly leaves them alone. If a rowset on its own is larger than the budget, it is never merged; raising --tablet_compaction_budget_mb carefully (memory use grows with input size) is the documented remedy in the log message.

Running a merge while the tablet keeps working

A merge compaction (and a MemRowSet flush, which uses the same function, Tablet::DoMergeCompactionOrFlush) takes a long time compared to a write, and the inputs keep receiving updates and deletes the whole time. Kudu's trick is two phases and a stand-in object.

What the merge writes. It reads the snapshot through a merging iterator over all inputs in key order, applies the REDO and UNDO deltas, and writes new base data plus fresh UNDO and REDO files. A row that was deleted and whose deletion is older than the ancient history mark is dropped entirely, and UNDO history older than the mark is not written. That is how deleted rows' space is finally reclaimed (a delete only marks the row until some merge removes it, part 6). Output is cut into rowsets of about the target size (32 MiB).

Why the no-op flush. If the output rowset were allowed to flush a delta file during phase 2 it could end up with a newer update in its first delta file than in the later one that gets added when missed deltas are copied over. REDO files must be ordered by time, so the duplicating rowset's FlushDeltas does nothing until the swap. (The comment in the source describes this exact sequence.)

Lock discipline. Swapping the duplicating rowset in takes the tablet's component lock in write mode, so no operation can start applying during the swap; then the compaction waits for operations that were already applying and counts them as committed in its second snapshot, so none of their updates is lost. The selected rowsets also have a per-rowset compaction/flush lock so two jobs cannot pick the same input.

Delta compactions: cheaper than a full merge

Updates are not applied to base data in place. They accumulate as REDO delta files, and each read of an updated row has to replay them. If a rowset has 200 tiny delta files, every read opens and consults 200 files. Delta compactions repair this without moving the rowset's keys.

Compaction and the history window

Part 12 pointed out that a tablet keeps history for --tablet_history_max_age_sec (7 days by default) so that snapshot reads and diff scans work. Compaction is where history is physically removed, and there are three separate mechanisms:

  • Merge compaction drops ancient rows and UNDO. When rewriting, it skips deleted rows older than the ancient history mark and omits UNDO deltas older than the mark.
  • UNDO delta block GC is a lightweight maintenance op: it deletes whole UNDO delta blocks that are entirely older than the mark. It does not rewrite anything, so it causes no write amplification. It has to read each UNDO block's stats once per process start, bounded to --undo_delta_block_gc_init_budget_millis (1000 ms) per run.
  • Deleted rowset GC deletes a rowset with no live rows whose most recent update is older than the mark.

The three interact with the merge policy. If more than --rowset_compaction_ancient_delta_max_ratio (0.2) of the UNDO data in the picked rowsets is ancient, the merge is held back (not runnable) so it will not waste I/O reading and rewriting data that UNDO GC will soon discard. This check is on by default (--rowset_compaction_ancient_delta_threshold_enabled).

Who decides when: the maintenance manager

Each tablet registers its ops with the tablet server's maintenance manager (part 7). Every few moments the manager asks each op for its stats and picks one. For compaction-family ops the important stats are:

Per-table controls. A table's extra config can carry a maintenance_priority (higher means its ops win ties) and can disable compaction for that table entirely (disable_compaction). When compaction is disabled, the compaction ops report themselves as not runnable and log a throttled warning. A tablet also refuses to schedule a merge until its MVCC "clean time" has advanced beyond the initial value, a guard against a known corruption (KUDU-2233).

An experimental flag, --enable_workload_score_for_perf_improvement_ops (default false), adds a "workload score" so ops of hot tablets are favored.

Signals. The tablet metric num_rowsets_on_disk and the compact_rs_duration, delta_minor_compact_rs_duration, delta_major_compact_rs_duration, flush_mrs_duration and flush_dms_duration histograms show how often each op runs and how long it takes. A table with ever-growing rowset counts and slow scans is the symptom of compaction not keeping up (disabled, blocked, or starved by higher-priority flushes under memory pressure).
