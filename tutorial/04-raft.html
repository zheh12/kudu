Raft in Kudu

Every tablet is its own small Raft group. Raft is what lets three copies of a tablet agree on the order of writes, survive the loss of a server, and elect a new leader without losing an acknowledged write. This part follows an operation through the leader, shows how elections and membership changes work, and ends with tablet copy.

One Raft group per tablet

A Raft group is a set of replicas that keep an identical, ordered log of operations. Each tablet replica has its own RaftConsensus object and its own write-ahead log (WAL). A tablet server that hosts 500 replicas therefore takes part in 500 independent groups, each with its own leader and its own term. The master's sys.catalog is just another tablet, so the same code keeps the masters in agreement.

Three words matter throughout. A term is a number that grows every time an election starts, and each term has at most one leader. An OpId is term.index, the position of an operation in the log. An operation is committed once a majority of voters have it in their WAL.

Replica roles and how they change

A replica is a VOTER or a NON_VOTER. Voters count towards majorities and can lead. Non-voters only receive the log, which is how a new replica catches up before it is trusted. Among voters, a replica is either a follower or the leader; being a candidate is a short-lived activity of a follower, not a stored role.

Replicating an operation

This is the leader's side of every write, schema change and membership change. The tablet layer hands the leader a ConsensusRound wrapping one operation. Consensus numbers it, writes it to the leader's own WAL, and ships it to each follower in parallel. When a majority has it, the commit index moves and the operation is applied.

Three indexes that describe progress

The queue keeps three watermarks over the log. They answer different questions, and the third one is the one that matters for safety.

What a follower checks before accepting

A follower does not trust the leader blindly. Every UpdateConsensus carries the OpId of the entry just before the new ones. The follower accepts the batch only if its own log has that entry. This one check is Raft's log matching property, and it is how divergent logs repair themselves.

Electing a new leader

Every follower runs a failure detector. It expects a message from the leader at least every 500 ms (raft_heartbeat_interval_ms), and gives up after three missed periods, 1.5 seconds. The give-up time is randomized with an exponential backoff after each failed attempt, so two followers rarely start at the same moment. Changing who is in the group

Servers fail and clusters grow, so the member list of a tablet has to change while it serves traffic. Kudu follows the one-at-a-time approach from Ongaro's thesis: a config change is itself a log entry, the leader allows only one pending at a time, and each change adds or removes a single replica. Changes are conditional (cas_config_opid_index), so two administrators cannot overwrite each other's decision.

A replica that is applying a config change uses the new configuration as soon as it has the entry, before commit, and only writes it to its consensus metadata when the entry commits. If the entry is aborted by a new leader, the replica falls back to the committed config.

Bringing in a new replica: tablet copy

A brand-new replica has no history, and the leader may have already deleted the old part of its log. So the leader does not replay everything. It tells the new server to copy the tablet from it: the data files, the tablet metadata and the WAL segments it still needs. After the copy, the replica is just a slightly lagging follower and catches up with normal UpdateConsensus calls.

The WAL and when it can be deleted

The WAL is the Raft log. It is a series of fixed-size segment files (8 MB each by default) with an index from op number to position. It serves two jobs: it is the durable log that consensus replicates, and it is the redo log the tablet replays after a crash. A segment can be deleted only when nobody needs it any more.

Practical rule: if a tablet is unavailable, ask first "do a majority of its voters respond?". The kudu cluster ksck and kudu tablet tools show each replica's role, term and last operation, and the tablet server web UI has a per-tablet consensus status page.
