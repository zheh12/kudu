Backup and restore

Kudu's supported backup is logical: a Spark job reads a table through the normal scan path and writes Parquet files, and a second Spark job writes them back. There is no built-in tool that copies tablet files from a running cluster. This part shows how the backup job gets a consistent view, how incremental backups chain together, how restore replays the chain, and what the only physical option looks like.

The big picture

Backup reuses machinery from earlier parts instead of adding new server features. The scan tokens of part 8 split a table into one unit of work per tablet. The snapshot read mode gives every unit the same timestamp, so the copy is consistent across tablets. The diff scan (a scan between two timestamps that also reports deleted rows) gives incremental changes. The only server-side requirement is that tablets keep history long enough (part 6, history GC).

One consistent snapshot

For each table the driver builds scan tokens with the read mode READ_AT_SNAPSHOT, cacheBlocks(false) (a backup should not evict hot data from the block cache) and CLOSEST_REPLICA selection, so a task can read from a nearby follower. The snapshot time is --timestampMs (default: now), converted to a hybrid timestamp. Because every tablet is read at the same timestamp, the backup is a point-in-time image even though the tablets are copied at different moments and the table keeps taking writes.

Spark gets a preferred location for each task: the replica hosts of the tablet, or the leader's host only if --scanLeaderOnly is set. Tasks keep their scanners alive while Spark is busy (--keepAlivePeriodMs), and results are written as Parquet.

Full and incremental backups

Each backup records a time range in its metadata: from_ms and to_ms. A full backup has from_ms = 0. An incremental backup starts where the previous one ended: its from_ms equals the previous backup's to_ms, and it is read with a diff scan between the two timestamps. The backups form a graph (BackupGraph) keyed by from_ms, and a chain is a path from a full backup through the increments.

How the job decides. With --forceFull it takes a full backup. If you pass --fromMs it takes an incremental from that time. Otherwise it reads the existing metadata under rootPath (found by table ID, so a renamed table is still linked), and if a full backup exists it starts an incremental from the base's to_ms; if none exists it takes a full one.

What an incremental contains. The diff scan returns changed rows plus an is_deleted flag. The job turns it into a RowAction column: DELETE (1) for deleted rows and UPSERT (0) for everything else. The comment in the code says it does not know whether a changed row was inserted or updated, so it records an upsert. A full backup has no action column.

Failure safety. Data files are written first and the metadata file is written last. A backup without its metadata file is ignored when linking and restoring, so a failed run leaves no half-visible backup. The data path includes the timestamp and must not already exist (SaveMode.ErrorIfExists).

What is on disk

Restore: replaying the chain

For each table the restore job reads all backup metadata under rootPath, keeps those with to_ms ≤ --timestampMs (default: now), and chooses a restore path: the chain with the most recent end time, then the fewest incrementals. It then applies the backups in order.

Useful restore options: --tableSuffix restores next to the live table, --createTables=false loads into an existing table, --newDatabaseName and --removeImpalaPrefix adjust names of Impala-managed tables, and --restoreOwner controls whether the table owner is restored.

Known limits stated in the docs and code comments: restoring tables with non-unique primary keys / auto-incrementing columns is not supported yet; if a restore fails partway, the table may be left created and a rerun then fails until the table is deleted or the suffix changed (KUDU-2832 in the source).

Why history retention matters

A snapshot read at timestamp T needs the data as it was at T, and a diff scan needs everything that changed since the previous backup. Tablets keep that history only for --tablet_history_max_age_sec, which defaults to 604,800 seconds (seven days) since Kudu 1.10. The flag description is explicit: it covers history needed for diff scans and incremental backups, and reads at a snapshot older than this age are rejected.

The physical option, and its limits

The guide says Kudu has no built-in physical backup, but a node can be copied by hand. It is a cold procedure: stop all Kudu processes in the cluster (so tablets are not re-replicated), copy the WAL, metadata and data directories preserving attributes and sparseness, and start again. Restoring means deleting the node's directories and putting the copy back. The warnings are important: the node must be offline or the copy will be inconsistent, and hostnames are embedded in the on-disk data, so a copy cannot be restored onto a different machine.

That makes it a node-level safety net, not a way to clone or migrate tables. For disaster recovery of tables, use the logical backup, ideally with the backup storage on a different system than the cluster. Remember replication (Raft) protects against server loss, not against someone running DROP TABLE; backups do.
