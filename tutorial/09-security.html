Learning Kudu · Part 9

Security: identity, secrecy and permission

Kudu has a complete set of security controls: Kerberos and token-based authentication, TLS encryption, access lists, Apache Ranger policies and encryption at rest. This part shows how they fit together. It starts with one fact that shapes the rest: most of them are off, or permissive, by default. A freshly started cluster expects to live on a trusted network.

The layers, and what each one does out of the box

Think of security as five questions: who are you, can anyone listen in, are you allowed, can someone read the disk, and what else can I see. Kudu answers each with a separate switch. The project's own threat model (THREAT_MODEL.md, still a draft awaiting maintainer review) states the posture directly: Kudu is designed to run inside a trusted cluster network, and the operator is expected to turn enforcement on.

Who proves what to whom

A secure Kudu cluster uses three kinds of credential, chosen so that the Kerberos server is contacted rarely. People and services start with Kerberos. After that, Kudu's own machinery takes over.

How trust is bootstrapped

The first time a server or client appears, it has nothing but a Kerberos identity. Here is how it ends up with Kudu credentials. Nothing is installed by hand on each node: the cluster hands out its own certificates through the heartbeat and connect paths you already know.

Authentication at connection time

Part 2 showed the negotiation steps. Here is the security meaning of the choices. The server picks one mechanism per connection, strongest first: a client certificate, then an authentication token, then Kerberos (or JWT where configured), and as a last resort SASL PLAIN. PLAIN carries no proof at all: the server accepts any user name.

Tokens: how a signature stands in for the KDC

The master signs two kinds of token with a private key. Everyone else holds only the public part and can verify without calling anyone. The private keys rotate daily, and the public parts are sent out ahead of time, so rotation never breaks a token.

Coarse permission: the ACLs

Once a user is identified, each RPC handler asks ServerBase::Authorize whether that user holds one of the roles the method accepts. There are three roles. Each is an access list of user names, with * meaning "any authenticated user".

Fine-grained permission: Ranger and authorization tokens

For per-table and per-column rules, Kudu (1.12 and later) uses Apache Ranger. The pattern is the same as for identity: ask the central service rarely, and carry the answer in a signed, short-lived token that every tablet server can check on its own.

Two limits to remember. Ranger rules are not enforced on the web UI, which can show data in places such as logs, scans and metrics, so limit or redact the UI. And since a tablet server relies on tokens issued by the master, the token lifetime (5 minutes) is also roughly the longest delay before a removed privilege stops working on a table a client already has open.

Encryption at rest

With --encrypt_data_at_rest, every file Kudu writes (WAL segments, data blocks, metadata) is encrypted with AES in counter mode, using 128, 192 or 256-bit keys. Keys form a chain, so that the disk never holds a key that opens its own data.

A checklist for a secure cluster

  1. Authentication. Give each server a Kerberos keytab (--keytab_file), then set --rpc_authentication=required on masters and tablet servers. Test a client with no ticket: it should be refused.
  2. Encryption in transit. Set --rpc_encryption=required. Decide about --rpc_encrypt_loopback_connections and the TLS protocol and cipher flags to match policy.
  3. Coarse ACLs. Replace --user_acl=* with the service accounts and users that need the cluster, and set --superuser_acl to the operators. If an engine such as Impala is your only client, list its service user and let it enforce row and column rules.
  4. Fine-grained policy (if you need per-table or per-column rules). Configure the Ranger client files, set the master's --ranger_config_path, --ranger_java_path, --ranger_jar_path and --trusted_user_acl, and set --tserver_enforce_access_control=true on every tablet server. Rename any tables whose names Ranger cannot handle (leading or trailing dot, names that differ only in case).
  5. Data at rest. On new clusters, --encrypt_data_at_rest=true with --encryption_key_provider=ranger-kms, --ranger_kms_url and an existing cluster key.
  6. Web UI and logs. Serve it over HTTPS, require SPNEGO or restrict the ports, and keep --redact=all.
  7. Network boundary. Even with everything above, keep master and tablet-server ports off the public internet. Leave --trusted_subnets alone unless you have a reason.
