The life of a row on disk

Kudu is a log-structured, columnar store, but it is not an LSM tree in the BigTable sense. Two design choices set it apart. A primary key lives in exactly one rowset, so a point read never merges versions from several files. And updates to flushed rows are stored as deltas addressed by row number, not by key, so they can be applied to a column without reading the key.

What a tablet holds

Part 5 used the phrase "the tablet's components". Concretely, a Tablet holds one MemRowSet and a RowSetTree, an interval tree of its DiskRowSets keyed by the smallest and largest primary key in each. A write or a point read asks the tree which rowsets could contain a key, and only those are probed.

Inside one DiskRowSet

A DiskRowSet is a small set of immutable blocks plus one mutable in-memory store. Rows are numbered 0, 1, 2 ... in key order inside the rowset. That row number is never stored. It is the position of a value in each column file. Every file in the rowset, and every delta, speaks in row numbers.

The file format: CFile

Each column, each delta file, the bloom filter and the key index are stored as a CFile: a sequence of data blocks, then index blocks that let a reader jump to a row number or to a key, then a footer. A CFile is written once, in order, and then read-only. Several CFiles can live inside one larger file on disk, as the block manager section below explains.

Flushing a MemRowSet

A flush turns the in-memory B-tree into DiskRowSets while the tablet keeps accepting writes. The trick is the same one that compactions use, so it is worth learning once: freeze a snapshot, write it out, then carry over whatever changed in the meantime.

UNDO and REDO: how history is kept

The MemRowSet keeps the oldest version of a row plus a list of later changes: a REDO chain. On disk the base data is the newest version, and the history behind it is an UNDO chain. A flush therefore inverts the chain. A scan of current data reads the base and ignores UNDO, which is the case the layout is optimized for. A scan at an older snapshot applies UNDO records backwards until it reaches its time.

What happens to updates after the flush

An update of a flushed row (Part 5, step 10) goes into the rowset's DeltaMemStore. From there it follows a short pipeline. The goal of the pipeline is to keep reads cheap: a read must look at the base data, then every REDO delta that is newer, so the fewer and smaller the deltas, the better.

Which rowsets get compacted

Compacting everything would give the best possible tablet and would rewrite all the data every time. The policy instead asks: given a fixed IO budget, which set of rowsets lowers the tablet's average height the most? It treats the total width of all rowsets as the cost of random access. Each rowset's width is the share of the key space it spans, which is also the chance that a random read has to look in it.

The scheduler: Maintenance Manager

Every job on this page is a MaintenanceOp registered by each tablet replica. A single MaintenanceManager per server polls them every 250 ms, asks each for fresh statistics, and starts the most valuable one when a worker thread is free. By default there is one worker thread, so the order matters.

One worker thread is the default (--maintenance_manager_num_threads=1). A heavily written server can fall behind on compaction while that single thread is busy with flushes. Raising it to the number of data disks is the first tuning step in the Kudu scaling guide. If tablets show growing numbers of rowsets or delta files, the scheduler is the first place to look.

Forgetting history

UNDO records are what make time-travel reads possible, so they accumulate with every update. Kudu keeps them for a retention period, --tablet_history_max_age_sec, seven days by default. Everything older than the "ancient history mark" (now minus the retention) is eligible for removal. Reads at a snapshot older than that mark are refused.

Where the bytes live: the block manager

A tablet with 30 columns and 20 rowsets has hundreds of CFiles. Putting each in its own filesystem file would be wasteful. The LogBlockManager appends many blocks into a few large container files. Each container is two files: a data file that holds block bytes, and a metadata file, a small log of "block X was created at offset Y" and "block X was deleted".

Symptoms and where to look. Writes rejected under memory pressure: flushes are not keeping up, check the maintenance thread count and disk speed. Reads slowing over time: look at rowset count and delta file counts per tablet in the web UI's tablet page. Disk use not shrinking after deletes or updates: UNDO retention, and whether merging compaction ran.
