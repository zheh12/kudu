Memory and disk: what lives where

A Kudu server must hold new writes in memory, keep a bounded cache of data it has read, and still finish every request without running out of RAM. This part lists every major consumer of memory and disk, says when data moves between them, and shows the layered limits that keep a busy server from overflowing.

The map: what is in RAM, what is on disk

Everything durable is on disk. Memory holds three kinds of things: data not yet written (it must be flushed), copies of data that is already on disk (a cache that can be dropped), and working space for requests in flight (released when each request ends). Only the first kind can grow without bound unless Kudu intervenes, which is why flushing and rejecting writes are the two safety valves.

Why the biggest consumer is the least obvious

Because a MemRowSet stores rows uncompressed, in a B-tree with per-row headers, it takes more memory than the same rows will take on disk, which is columnar, encoded and optionally compressed. A "hot" replica, one that is continuously written, can therefore hold hundreds of megabytes of memory before its flush is worth doing. The scaling guide uses 128 MB per hot replica as a planning number. Multiply by the number of hot replicas on the server, and the product is usually the largest bar in the budget.

Three thresholds that keep memory in check

One number, --memory_limit_hard_bytes, sets three lines. They apply to the whole process, measured as the bytes the allocator has handed out, not to any one component. At each line, the server does something different.

Why the block cache is capped below the pressure line. Cached blocks cannot be flushed, only evicted. If the cache alone exceeded 60%, the server would sit in "pressure" with nothing useful to flush, and would flush every MemRowSet constantly. Since Kudu 1.8 the server refuses to start if --block_cache_capacity_mb is above the pressure threshold, and logs a warning above half of it. With defaults, keep it under about 30% of the hard limit.

Defense in layers: every queue has a bound

The memory limits are the last line of defense. Before a request can cost much memory, it must pass a series of smaller bounds. Each layer rejects early and cheaply, so the server stays responsive and the client backs off.

The disk budget

Disk fills more predictably than memory but has its own traps. The WAL, the data files and the transient copies made during compaction compete for space. The first two are bounded by policy; the third is a spike you must leave room for.

A tuning recipe

  1. Set the hard limit on purpose. Estimate the expected usage (data on disk × 1.5 GB per TB, plus about 128 MB per hot replica, plus scanners and the cache) and set --memory_limit_hard_bytes so that this is 50 to 75% of it. Leave room for the operating system and other processes. Do not rely on the 80%-of-RAM default on shared hosts.
  2. Size the block cache for reads, not for writes. Keep --block_cache_capacity_mb at or below about 30% of the hard limit. Raise it only if block_cache_misses_caching and evictions are large against inserts.
  3. Make flushing faster than ingest. Add maintenance threads (about one per three data directories) and put data on enough disks. Memory problems that look like "not enough RAM" are often "flushes cannot keep up".
  4. Reduce the number of hot tablets. Every actively written tablet holds a MemRowSet. A table with 1,000 hash buckets receiving uniform writes keeps 1,000 MemRowSets warm, though a lower bucket count would spread the load just as well. Also keep tablets per server within the limits in the known-issues page.
  5. Shape the clients. Batch writes, keep batches moderate (a few thousand rows), and let the client's built-in retry back off. Sorted keys within a batch make the presence check cheaper.
  6. Set the WAL and data directories apart, and reserve enough free space for compaction and tablet copy.
