Monitoring and metrics

A Kudu cluster tells you what it is doing in several ways at once: a built-in metrics system, web pages on every daemon, a periodic metrics log, warning traces in the logs, and a health-check command. This part draws the map, explains how metrics are modeled (entities, types, levels), shows how to scrape them with Prometheus, and ends with a short list of signals worth alerting on, taken from the metrics that Kudu itself tags as warnings.

Six sources of signal

Every daemon (master and tablet server) has an embedded web server. Masters use port 8051 by default and tablet servers 8050. Most of what you need hangs off it, and the rest is in log files and the kudu command-line tool.

How metrics are modeled

The metrics library (util/metrics.h) has three ideas. A prototype declares a metric: its name, unit, description and level, defined statically with METRIC_DEFINE_* macros, so the full list of possible metrics is known at build time (that is why the reference page can be generated, and kudu-tserver --dump_metrics_json can print every metric without running a cluster). An entity is a thing being measured: the server process, a tablet, or a table. Each entity instance has a unique ID and string attributes, and owns its own instances of the metrics defined for its type. A metric is then an instance: a counter, gauge or histogram.

Types. A counter only goes up (rows inserted, RPCs dropped); a gauge is a sample that can go up or down (memory in use, tablets failed); a histogram records the distribution of a value, such as latency, using configurable range and precision, and exports percentiles (from 0 to 1 including 0.75, 0.95, 0.99, 0.999 and 0.9999). Some gauges are exposed as counters when they are logically cumulative (the EXPOSE_AS_COUNTER flag).

Retirement. When a tablet is deleted or moved, its metrics are not dropped immediately. They are kept for --metrics_retirement_age_ms (120 s) so a scraper that polls once a minute still sees the final values. Expect a deleted tablet's series to linger for about two minutes.

Prometheus

Each daemon serves /metrics_prometheus, and the master also serves /prometheus-sd, a service-discovery document. The master knows every master and every tablet server, so a Prometheus job can use it to find all targets instead of a hand-maintained list. It returns target groups in the usual file-based format, with HTTP addresses as targets and labels for the group, the cluster ID, the location and the scheme (http or https).

What to alert on

Kudu tags the metrics most likely to indicate trouble with the warn level, so /metrics?level=warn is a ready-made starting list. The groups below organize metrics the source marks as warn (descriptions are the source's own), plus a few info-level gauges you want on a dashboard. Thresholds depend on your workload, so none are given here.

On the clock. Kudu's hybrid clock (part 5) needs good time. hybrid_clock_extrapolating is true when timestamps are being extrapolated because the underlying clock cannot be read, and hybrid_clock_error reports the current error bound. The troubleshooting guide's NTP section describes how to set up and watch ntpd or chronyd.

ksck: asking the cluster about itself

kudu cluster ksck <master addresses> contacts the masters and every tablet server, compares what the catalog says should exist with what servers report, and prints summaries: masters, tablet servers, versions, per-table health, and totals. It exits non-zero if there is a problem, so it fits in a scheduler or a deploy check. The admin guide says it identifies under-replicated tablets, unreachable servers and tablets without a leader.

  • Per-table status columns: replication factor, total tablets, and counts of healthy, recovering, under-replicated and unavailable tablets.
  • Limit the scope with --tables or --tablets; get detail on one tablet's replicas and Raft config that way (the admin guide uses it when diagnosing a stuck tablet).
  • Data integrity: --checksum_scan reads every replica of the selected tablets (snapshot scans by default) and compares checksums. Expensive: do it off-peak and scoped.
  • Machine-readable output: --ksck_format includes a JSON option for other tools.
  • Run ksck before and after any maintenance (restarts, adding servers, rebalancing, directory changes); the administration guide says so throughout.
Other CLI helpers: kudu tserver list and kudu tserver status for servers, kudu tserver get_flags and set_flag for flags, kudu table list and describe for tables, and kudu diagnose parse_metrics / parse_stacks for diagnostics logs.
