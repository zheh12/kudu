The Kudu RPC framework

Every arrow in Part 1 is an RPC: client to master, tablet server to master, leader to follower. They all run on one small framework in src/kudu/rpc/. This part shows how a call travels, what it looks like on the wire, and how it survives retries.

The big picture

Kudu RPC is protocol buffers over TCP, with libev (epoll) for non-blocking I/O. Its wire format is close to Hadoop IPC. The same Messenger object serves both directions: it sends your outgoing calls and receives the incoming ones. A few reactor threads move bytes, and a separate pool of worker threads runs your code, so slow handlers never stall the network threads.

You write a .proto, the build writes the plumbing

A service is declared in a .proto file. A custom protoc plugin, protoc-gen-krpc, emits two C++ classes from it. Clients call the proxy. Servers subclass the interface. Neither side writes serialization or dispatch code.

Design tip from the docs: for errors the client should act on, put an error field inside the response protobuf. A plain RPC failure only carries a status string.

Following one call

Four threads are involved in a single call: the caller, the client reactor, the server reactor and a server worker. This is the order of events, and the thread that owns each step.

Threads and queues on the server

The server keeps network work and application work apart. A connection is pinned to one reactor for life, chosen by hashing the peer's address. New connections spend a moment in a separate negotiation pool, so a slow handshake cannot block a reactor. Calls then wait in a bounded queue before a worker takes them.

What goes over the wire

After the one-time connection header, every message is a length-prefixed frame holding two protobufs: a header that says what the message is, and a body with your data. The same framing carries requests, responses and negotiation messages.

Opening a connection: negotiation

Before the first call, the two sides agree on features, optionally set up TLS, and prove who they are. This is why the first RPC to a new server is slower than later ones. Connections are then reused for the life of the process.

Retries without double writes

Networks drop responses. If a client resends an insert whose reply was lost, the row must not be inserted twice. Kudu solves this with exactly-once semantics for methods marked track_rpc_result. The client tags each logical call with a stable id, and the server's ResultTracker remembers the outcome.

Retries and failover to another server are driven on the client by RetriableRpc (rpc/retriable_rpc.h) with a ServerPicker. Kudu's data-path clients layer table-aware logic on top, which is why a write that hits a former leader refreshes the MetaCache and retries without the application noticing.

Debugging tip: the tablet server and master web UIs serve /rpcz, which lists open connections and the calls in flight, and /metrics includes rpc_incoming_queue_time and rpcs_queue_overflow. Rising queue time with a full queue means the service pool is the bottleneck, not the network.
